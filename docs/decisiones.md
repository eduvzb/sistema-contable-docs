# Decisiones vigentes

Registro único para acuerdos compartidos. Las decisiones limitadas a una funcionalidad viven en su spec. Para cambiar un acuerdo, registrar fecha, motivo, qué reemplaza y specs afectadas; no crear un ADR por cada tarea.

| DP-003 | El ciclo SDD incluye el estado `Actualización pendiente` para una funcionalidad existente cuyo cambio de comportamiento ya está preparado, pero aún no cuenta con implementación y comprobaciones técnicas completas. Conserva separadas la evidencia anterior y la pendiente. | Instrucción explícita del usuario, 2026-09-10. |
| DP-004 | El ciclo SDD incluye el estado `QA`: implementación y comprobaciones técnicas completas, con sólo la validación visual humana pendiente. La comprobación integral de interfaz por navegador no es responsabilidad ni criterio de cierre del agente; únicamente una persona aprueba QA y mueve la spec a Implementada. | Instrucción explícita del usuario, 2026-09-10. |
| DP-005 | Cada tarea de código crea desde `main`, sólo en los repositorios de implementación afectados (backend y/o frontend), una rama `codex/<tipo>/SPEC-NNN/<slug>`. `<tipo>` es uno de `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `build` o `ci`; `<slug>` es una descripción no vacía en kebab-case (`[a-z0-9]+(?:-[a-z0-9]+)*`). Antes de crear ramas, se elige un único nombre disponible local y remotamente en todos los repositorios afectados; si el candidato ya existe en cualquiera, se prueba el mismo nombre con el menor sufijo libre `-2`, `-3`, etc., sin reutilizar la rama ocupada. El árbol debe estar limpio, `origin` debe existir, `gh` debe estar instalado y autenticado con acceso al repositorio. Cada repositorio de implementación termina con un único commit descriptivo (`SPEC-NNN: verbo en imperativo`) y publica la rama elegida con `git push -u origin "$RAMA_TRABAJO"`. Después crea o reutiliza mediante `gh` un PR normal con base `main` y head `RAMA_TRABAJO`; un PR abierto que coincida exactamente se reutiliza y cualquier fallo o colisión detectada al publicar bloquea el cierre. El repositorio de specs conserva su rama actual y puede recibir evidencia documental sin rama, commit, push ni PR de implementación obligatorios. El cierre espera a todos los repositorios de implementación afectados y no realiza merge automático. | Instrucción explícita del usuario, 2026-09-12; reemplaza la nomenclatura única registrada el 2026-09-10. |
| DT-012 | Todo comportamiento interactivo nuevo o modificado en el frontend Next/React se comprueba con pruebas de componentes y comportamiento mediante Vitest, `jsdom`, React Testing Library, `@testing-library/user-event` y matchers de `@testing-library/jest-dom`. Las pruebas observan roles, etiquetas, contenido, foco, eventos y efectos públicos; los snapshots no sustituyen los criterios. `pnpm test` ejecuta la suite reproducible. Las pruebas integrales por navegador no son requisito de cierre y las existentes pueden permanecer sin ejecutarse; `jsdom` no acredita layout, superposición, dimensiones ni scroll reales, que corresponden a QA visual humana. La decisión aplica prospectivamente y no invalida evidencia histórica ni modifica las pruebas backend/API o de integración entre módulos. | Instrucción explícita del usuario, 2026-09-12. |
| DT-013 | Los XML nuevos importados o provenientes de la descarga simulada se procesan en la solicitud y sólo persisten sus datos fiscales normalizados, relaciones y trazabilidad contable. No se guarda el archivo en almacenamiento durable ni como BLOB, y no existe API de descarga del original. Los archivos históricos se conservan sin acceso desde el producto ni purga automática; una purga futura requiere autorización explícita. El temporal de una carga multipart administrado por la plataforma es aceptado. | Instrucción explícita del usuario, 2026-09-14; reemplaza BR-011 anterior. |

- **2026-09-10:** se registró DP-003 y se amplió el flujo SDD con `Actualización pendiente` para distinguir claramente las specs reclasificadas por cambios posteriores.
- **2026-09-10:** se registró DP-004: QA humana sustituye la comprobación integral por navegador dentro del trabajo del agente y separa el cierre técnico de la aprobación visual.
- **2026-09-10:** se aclaró DP-005: las ramas, commits y publicaciones de ejecución aplican sólo a backend/frontend; el repositorio de specs conserva su rama actual y no se publica como parte de esa ejecución.
